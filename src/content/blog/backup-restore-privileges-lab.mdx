`SeBackupPrivilege` and `SeRestorePrivilege` are frequently summarized as
“bypass every file ACL.” That shorthand hides the details that matter during an
audit.

According to Microsoft's privilege definitions:

- `SeBackupPrivilege` can grant read-oriented rights to files regardless of the
  file DACL, including `READ_CONTROL`, `FILE_GENERIC_READ`, and traversal;
- `SeRestorePrivilege` can grant write-oriented rights, including
  `FILE_GENERIC_WRITE`, `WRITE_DAC`, `WRITE_OWNER`, add-file/add-subdirectory,
  and delete;
- unrelated requested access is still evaluated normally;
- the privilege must be present in the token, enabled when required, and used
  through an operation that recognizes backup or restore intent.

This is powerful, but it is not “all access everywhere.”

## Presence, state, and use are different

Run:

```powershell
whoami /priv
```

The output can show a privilege as:

- absent — it is not part of the token;
- present but disabled — the process may try to enable it;
- enabled — an API can consider it for the relevant operation.

`AdjustTokenPrivileges` cannot add a privilege that is absent from the token. It
only changes attributes for privileges already assigned. The function's Boolean
return value reports whether the function itself ran; it can return nonzero and
still set `ERROR_NOT_ALL_ASSIGNED`.

Correct code checks both.

## A reusable privilege-enabling helper

```cpp
#include <windows.h>
#include <iostream>

bool EnablePrivilege(const wchar_t* privilegeName) {
    HANDLE token = nullptr;
    if (!OpenProcessToken(
            GetCurrentProcess(),
            TOKEN_ADJUST_PRIVILEGES | TOKEN_QUERY,
            &token)) {
        return false;
    }

    LUID luid{};
    if (!LookupPrivilegeValueW(nullptr, privilegeName, &luid)) {
        CloseHandle(token);
        return false;
    }

    TOKEN_PRIVILEGES update{};
    update.PrivilegeCount = 1;
    update.Privileges[0].Luid = luid;
    update.Privileges[0].Attributes = SE_PRIVILEGE_ENABLED;

    SetLastError(ERROR_SUCCESS);
    const BOOL adjusted = AdjustTokenPrivileges(
        token, FALSE, &update, sizeof(update), nullptr, nullptr);
    const DWORD status = GetLastError();
    CloseHandle(token);

    if (!adjusted) {
        std::wcerr << L"AdjustTokenPrivileges failed: " << status << L"\n";
        return false;
    }
    if (status == ERROR_NOT_ALL_ASSIGNED) {
        std::wcerr << L"Privilege is not present in this token\n";
        return false;
    }
    return status == ERROR_SUCCESS;
}
```

Call it with the SDK names:

```cpp
EnablePrivilege(SE_BACKUP_NAME);
EnablePrivilege(SE_RESTORE_NAME);
```

Do not silently continue after `ERROR_NOT_ALL_ASSIGNED`; that turns a failed
precondition into confusing access-denied errors later.

## Backup intent changes file-open semantics

`CreateFileW` accepts `FILE_FLAG_BACKUP_SEMANTICS`. The flag is also required to
obtain a handle to a directory with `CreateFile`. For a process holding the
appropriate privilege, it signals that the open is for backup or restore
operations.

This lab function requests read access only:

```cpp
HANDLE OpenForBackupRead(const wchar_t* path) {
    if (!EnablePrivilege(SE_BACKUP_NAME)) {
        return INVALID_HANDLE_VALUE;
    }

    return CreateFileW(
        path,
        GENERIC_READ | READ_CONTROL,
        FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE,
        nullptr,
        OPEN_EXISTING,
        FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT,
        nullptr);
}
```

Two choices are deliberate:

- the access mask does not ask for write or execute rights;
- `FILE_FLAG_OPEN_REPARSE_POINT` lets a lab inspect the named object rather than
  automatically following a reparse point.

Real backup software often uses `BackupRead` and `BackupWrite` to preserve
alternate data streams and security information. A simple `ReadFile` example is
enough to demonstrate the access decision, but it is not a complete backup
implementation.

## Build a safe protected-file lab

From an elevated PowerShell console, create a dedicated directory and file:

```powershell
$root = "C:\KwpwnBackupLab"
$file = Join-Path $root "protected-note.txt"

New-Item -ItemType Directory -Path $root -Force | Out-Null
Set-Content -LiteralPath $file -Value "LAB DATA ONLY"

$acl = Get-Acl $file
$acl.SetAccessRuleProtection($true, $false)
$acl.Access | ForEach-Object { [void]$acl.RemoveAccessRule($_) }

$adminRule = [Security.AccessControl.FileSystemAccessRule]::new(
    "BUILTIN\Administrators",
    "FullControl",
    "Allow"
)
$systemRule = [Security.AccessControl.FileSystemAccessRule]::new(
    "NT AUTHORITY\SYSTEM",
    "FullControl",
    "Allow"
)
$acl.AddAccessRule($adminRule)
$acl.AddAccessRule($systemRule)
Set-Acl -LiteralPath $file -AclObject $acl
```

The file contains no secret and exists only to make the access decision visible.
Before running any backup-aware program, confirm that an ordinary read from the
standard-user context fails:

```powershell
Get-Content -LiteralPath C:\KwpwnBackupLab\protected-note.txt
```

That failure is the negative control.

Next, run the compiled inspection program under a token that was intentionally
assigned `SeBackupPrivilege` in this disposable lab. Record:

1. the token's user SID and privilege state;
2. whether enabling succeeded;
3. the requested access mask and flags;
4. the `CreateFileW` result and `GetLastError`;
5. the file SDDL before and after.

The read should not modify owner, DACL, timestamps, or content.

## Restore semantics are not a reason to overwrite

`SeRestorePrivilege` is more dangerous to validate because it grants
write-oriented rights and can permit owner and DACL changes. Use a second lab
file and a harmless metadata operation. Do not point restore code at Windows,
Program Files, registry hive files, or user profiles.

A safe research question is:

> Can this token open the lab file requesting `WRITE_DAC` when restore privilege
> is enabled and backup semantics are supplied, while the same open is denied
> when the privilege is disabled?

The test need not call `SetFileSecurity`. The granted handle is sufficient to
show that the access check differs. Close the handle immediately and compare the
object's hash and SDDL.

## Directories, reparse points, and traversal

Backup software walks trees, so directory and reparse behavior matters.
`SeBackupPrivilege` includes traversal-related capability, but following a
reparse point can move an operation outside the intended tree. A safe backup
tool should:

- open the reparse point itself when classifying it;
- inspect its tag;
- maintain a boundary policy for destinations;
- avoid assuming that a path string still identifies the same object after a
  race;
- record file identity when correctness matters.

Privilege answers “may this operation bypass a DACL?” It does not solve path
confusion, race conditions, or reparse-point safety.

## Why backup privileges appear in escalation write-ups

A non-administrative service account with backup rights may be able to read
otherwise protected material. A token with restore rights may be able to replace
or re-permission files consumed by a privileged component. The resulting impact
depends on the reachable object and subsequent consumer.

Avoid collapsing capability and impact:

- **Capability:** read a protected lab file with backup semantics.
- **Potential impact:** access sensitive files the account was not meant to
  read.
- **Escalation chain:** use a permitted read or write to influence a
  higher-privileged authentication or execution boundary.

The third statement needs its own evidence. Do not use credential database
extraction as a default lab demonstration.

## Detection and hardening

Defenders should focus on assignment and use:

- keep “Back up files and directories” and “Restore files and directories”
  limited to dedicated, managed service identities;
- separate backup operators from interactive logon where practical;
- monitor changes to user-right assignment;
- correlate privileged file access with process identity, signature, command
  line, and expected backup windows;
- alert when a backup-capable identity accesses unrelated application or
  credential paths;
- rotate and remove stale service accounts.

An enabled privilege in a token is context, not proof of misuse. A defensible
detection joins identity, unusual target, process lineage, timing, and operation.

## Decompose the access decision

Do not treat a successful open as evidence that a privilege was used. The same
request can succeed because the DACL already grants access, the caller owns the
object, the file is opened with backup intent while an applicable privilege is
enabled, or the test accidentally ran elevated.

Capture the decision as a matrix:

| Variable | Values worth testing |
| --- | --- |
| token | privilege absent, present-disabled, present-enabled |
| object DACL | ordinary read/write allowed, denied to test identity |
| open options | normal semantics, documented backup semantics |
| requested access | metadata only, content read, content write |
| caller | standard interactive token, dedicated lab account |
| path | ordinary file, protected test file, directory, reparse boundary |

Change one cell at a time. The strongest demonstration is differential:

1. the protected test file cannot be opened for the requested operation with
   the privilege disabled;
2. the same token enables the named privilege and retries the same operation;
3. the operation succeeds only when the documented backup/restore semantics
   are used;
4. disabling the privilege again restores the denial;
5. an ordinary file remains accessible in all expected control runs.

Record the `AdjustTokenPrivileges` return value **and** `GetLastError`.
Successful return does not mean every requested privilege was assigned; the
documented `ERROR_NOT_ALL_ASSIGNED` result distinguishes a privilege missing
from the token from a privilege that was present and enabled.

## Worked lab: protected marker, not credential material

Create a dedicated local lab account and a directory that contains a harmless
text marker. Apply a DACL that denies ordinary content access to that account
while leaving the administrator recovery path intact. Before changing
permissions, export the original security descriptor so cleanup is
deterministic.

Run four observations and keep the file contents constant:

| Run | Privilege state | Open behavior | Expected interpretation |
| --- | --- | --- | --- |
| A | disabled | ordinary read | denied by the object access check |
| B | enabled | ordinary read | may remain denied; privilege presence does not rewrite every API contract |
| C | enabled | documented backup semantics | content retrieval can bypass the ordinary DACL path |
| D | disabled again | same as C | denied, establishing the privilege dependency |

For a restore-side exercise, use a second disposable marker and validate only a
benign metadata/content restoration into the lab directory. Do not overwrite a
service binary, authentication database, boot file, or another security
principal's profile. Preserve before/after hashes, owner, DACL, attributes, and
timestamps so the report says exactly which property changed.

Add two negative controls:

- repeat the operation under a token that does not contain the privilege and
  confirm that enabling it reports `ERROR_NOT_ALL_ASSIGNED`;
- repeat against a path reached through a reparse point after refusing the
  traversal, proving that the lab helper does not silently follow an
  attacker-controlled namespace change.

This proves the primitive without turning the lesson into a credential-access
recipe.

## Filesystem and version scope

The user-right names are stable policy concepts, but observed behavior also
depends on the filesystem, API, open flags, object type, filter drivers, and
Windows build. Keep these claims separate:

- **documented:** `SeBackupPrivilege` can permit retrieval of file content even
  when the file security descriptor would not normally grant access;
- **documented:** `SeRestorePrivilege` can bypass ordinary checks for some
  restore-oriented writes;
- **environment-dependent:** which metadata, alternate streams, reparse data,
  encryption state, or remote-share behavior the selected API preserves;
- **not established by the token alone:** that any sensitive target is
  reachable or that a privileged consumer will use restored content.

Test local NTFS and any other relevant filesystem separately. A remote share
adds server-side authorization and protocol behavior; do not generalize a
local result to SMB. Record edition, build, filesystem, volume policy, API,
flags, account rights, token state, and any minifilter that can affect the
operation.

## Evidence and reporting gate

| Claim | Minimum evidence |
| --- | --- |
| privilege is assigned | token enumeration or policy record |
| privilege is enabled | token state immediately before the operation |
| ordinary access is denied | exact access request and error under a control run |
| privileged semantics changed the result | paired run with one variable changed |
| object content or metadata changed | before/after hash and security metadata |
| escalation is possible | separate proof of a higher-privileged consumer and controlled input |

A high-quality report stops at the strongest proven row. If the lab establishes
only protected-file retrieval, say so. The additional claim "this produces
elevation" requires evidence for a writable or readable target, a privileged
consumer, a trigger, and a security boundary crossed.
